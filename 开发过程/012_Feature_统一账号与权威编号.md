# 012 Feature 统一账号与权威编号

> 日期：2026-08-13
> 状态：Phase 8A 已实现并完成本地自动化自测；未独立安全审查或部署

## 背景与用户故事

旧流程先创建产品用户，再单独注册或绑定 AI Card，与“AI Card 是全体系唯一账号”的产品定义冲突。本阶段建立唯一发行中心：人类首次注册时自动获得永久 AI Card，AI 邀请也使用同一发号器。

作为首次用户，我希望只填写一次昵称、Handle 和密码，系统就签发永久 `AI_100001` 形式身份并建立会话；之后用永久编号或 Handle 登录，不再重复注册或绑卡。

## 关键决策

- 内部 Principal ID 继续使用 UUIDv7；公开 `AI_` 顺序编号不承担数据库关系主键。
- PostgreSQL sequence 和 insert trigger 是唯一发号权威。Repository、API、Yoyoo 和 Agent 都不能指定下一号。
- 迁移按现有 Card 的 `created_at, principal_id` 稳定顺序分配新编号，同一事务内改写 Handle 和邀请外键；旧 `aic_...` 值写入只读别名表保留历史链接。
- 注册在一个事务内创建 Principal、Card、Handle、密码凭据、幂等记录、会话和审计，失败时不留部分身份。
- 密码使用每账号随机 salt 的 `scrypt`。Passkey 保留为可选增强凭据，密码账号可添加首个 Passkey。
- 幂等键只解决重复提交，不能作为登录凭据；恢复同一注册结果时仍必须验证原密码。
- 未知账号、错误密码、失效 Card 和 disabled 凭据使用同一对外错误，且未知账号仍执行等价 KDF 计算。

## 否掉的备选

- 继续用随机长 `aic_...` 作为公开编号：安全性可接受，但不符合可记忆、可口述的产品目标。
- 让 Yoyoo 继续生成 `AI_` 编号：会形成多个发卡权威，无法保证全体系唯一。
- 用 Card ID 替换 Principal ID 作外键：会把可公开表达与内部真实身份耦合，增加迁移与枚举风险。
- 把幂等键视为可恢复会话的秘密：幂等键泄露后可导致账号接管，因此重试仍校验原密码。
- 在本阶段直接修改 Yoyoo 生产权威：跨仓库与历史资源迁移的爆炸半径更大，必须作为独立 Phase 8C 先备份、对账和演练。

## 影响范围

- 新增 `0009_unified_ai_card_ids.sql` 和 `0010_password_accounts.sql` 两条 forward migration，未修改历史 migration。
- 所有人类、AI 邀请和 Passkey 初始注册 Card 创建路径改为数据库发号。
- 新增密码注册/登录 API、账号入口和可选 Passkey 升级。
- 公开 Card 查询保留旧 ID 别名兼容；新 API 和页面使用 `AI_...`。
- 未新增第三方依赖；密码 KDF 使用 Node.js 标准 `crypto.scrypt`。
- 未修改 Yoyoo 生产库、部署或现有公网登录行为。
